## What can go, and what LAWS keeps

Ranked by CPU on this clean pass. Wall time of a guard read is the engine's settle wait (about
400 ms after input, about 50 ms before it). The ranks use the measured process CPU.

1. Failed textedit-save, 8.6 s own CPU, 3.7 s of it engine. The harness already clears restored
   TextEdit windows (`docs/benchmark.md`). A further guard change leaves this CPU in place. The task's
   file check stays. These two runs failed it.

2. Calculator's per-click `getAXState({ disableDiffing: true })` before each action after the
   first, 17 reads, and the task's +2.0 s engine plus +1.0 s of Calculator's own CPU. This is the
   only positive engine gap on runs both arms passed. LAWS keeps it. Numbered actions and actions
   by ID or label read before the action. A read after a click stays, so the next key is sent to
   a sheet that click opened. Deleting the read drops those checks. `timedRead` in
   `document-scope.mjs` is the call. A diff in place of `disableDiffing: true` still asks the
   engine for a post-input read, so the helper walk and the settle wait stay. A keypad diff that
   omits the button line fails closed into the same full read. The check then costs the same full
   read. This is the gap, and the read stays.

3. The after-call read (`guardedCode`'s `readAfter`, same file). 1.04 s wall on two failed runs,
   zero reads on the seven passes. ROADMAP already keeps it. The lease and the engine's diff
   baseline want one full tree after the call. `plugins/sleight/lib/compact-reads.mjs` says the
   guard read with diffing off is that baseline. Cutting it drops that check. Passing runs spent
   0 s on it.

4. osascript, 1.54 s in the sleight bucket (0.28 s of it on calculator-click). Every app read
   also probes whether the window is on the current Space (`plugins/sleight/lib/relay.mjs`, the
   `spaceProbe` call beside the engine read), because an Open panel and the document behind it
   can disagree. Dropping the probe on Calculator keeps the TextEdit case and saves about 0.3 s
   a pass. That saving is too small for the first change.

5. Screenshots, 0 s on this suite. Leave `getScreenshot` as it is.

## First change to build

Add a skip for the guard's before-action read on later clicks in a call. Keep it off the default
until the owner amends the LAWS line that keeps that read.

In `act()` inside `guardSetup` (`plugins/sleight/lib/document-scope.mjs`), when
`SLEIGHT_GUARD=batch` and all of the following hold, skip `timedRead` and resolve the target
from the tree already in `state.callElements`, the same way a `skipped` quiet action does today:

- This call has already stored one full before-action tree (`state.callElements` has this handle).
- The previous action was `click`, and this action is `click` by a number, an `{ id }`, a
  `{ label }`, or a bare name.
- The stored line for that target contains `ID:` or `Description:`, and that line is the only
  match. Zero matches or several matches keep today's `timedRead`.
- `SLEIGHT_GUARD=careful` still reads before every action. The default, with the variable unset,
  still reads too.

The first action in the call still reads. The read after a shortcut, Return, Escape, Tab or Space
still runs, because those open a sheet. The after-call `readAfter` stays
`getAXState({ disableDiffing: true })`. The lease header and the diff baseline still update once
per call. ID and number checks still run on the stored tree. A renumber from the click just
before is invisible to those checks. That is the check LAWS keeps, and the reason the default
stays on the full read until the owner changes the law.

Tests in `tests/guard-reads.test.mjs`. With `SLEIGHT_GUARD=batch`, a second click whose stored line is a
unique `ID:` skips `getAXState`. The after-call read still calls it. A missing or duplicate ID
calls `getAXState` once before the click. `careful` calls it before every click. A click after
Return still reads.

The live check, for sleight-arch, is calculator-click, 3 runs each of default and `batch`, owner
away, traced. The number that decides it is engine CPU on the task, 6.5 s for sleight against
4.6 s for Codex on this pass, plus own CPU. The task passes 3/3 on both sides. textedit-edit
runs 3/3 on `batch` as well. That task's engine CPU is already under Codex (6.9 s against 7.7 s)
and has to stay there. Keep the default unless `batch` cuts calculator engine CPU by at least
1.0 s across the three runs.
