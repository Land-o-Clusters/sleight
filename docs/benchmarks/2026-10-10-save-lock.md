# TextEdit save-lock investigation, 2026-10-10

No document edit or save comparison completed. The stopped runs are preserved below.
The existing Shift mitigation remains unchanged. Its earlier 0/10 hangs against 5/8 without Shift
does not tell us which event or document activity matters.

## Earlier evidence

The local research note of 2026-10-08 read AppKit disassembly and earlier TextEdit logs. It found
no coordinated file write between the Accessibility edit and the hung save. It proposed that an
activity started by the edit awaited a main-thread callback. That remains an inference because
the earlier probes ended before AppKit's reported activity-dump delay.

The Shift mitigation posts two `flagsChanged` events to TextEdit's PID, with Shift set and then
cleared. It doesn't change text or use a HID event stream. Event delivery could finish pending
document work or reschedule an autosave monitor. Modifier state and the added delay are also
possible causes, which the earlier results do not distinguish.

## Probe

`node bench/textedit-save-lock.mjs --quick` compares no event, a Shift pair, a zero-modifier
`flagsChanged`, a Shift release alone and Escape. Each arm starts a new background TextEdit process
with an owned plain-text file under `/private/tmp`, writes a distinct value through Accessibility,
waits ten seconds, posts Cmd+S to that PID and compares the saved bytes with the buffer. The default
uses three trials per arm. Each saved fixture closes before its retained process receives a quit.

The probe stops on the hold marker, a taken live lock, a dialog, a changed foreground app, an
ambiguous new PID, an extra window or a mismatched document URL. It leaves existing TextEdit
processes alone. Unconfirmed fixture or process cleanup retains the live lock. It doesn't use an
engine, clipboard, pointer event, activation or Open panel. An Open-panel reproduction and the effect of
the engine's own save events remain outside this comparison.

## Review correction

The read-only check above violated the live hold. It also left the owned TextEdit process running,
so its exit 0 did not establish complete cleanup. The receipt is retained as failed evidence.
Both native helpers now check the hold before live reads or actions. The cleanup runner checks it
before inspecting or acquiring the lock, including in read-only mode. A closed fixture no longer
counts as a quit process. Cleanup can reacquire an absent lock. After checking the recorded PID
and launch time, it quits only that launch if it has no windows. Restored windows still stop a quit.
The trial runner also attempts this cleanup after an unedited attach failure and helper collection.
The [follow-up handoff](2026-10-10-sim-savelock-2.md) records the remaining owned-process cleanup.
