# TextEdit save-lock experiment, 2026-10-10

Plugin behavior is unchanged. No live run on this branch.

After an Accessibility text write, TextEdit's next Cmd+S deadlocked on the document's save
lock in 10 of 13 trials on 2026-10-08 when the file was opened through the Open panel, and in
0 of 3 opened with `open -g` ([known problems](../known-problems.md)). Those hangs used the
engine's `pressKey("super+s")`.

On 2026-10-11, Cmd+S posted to a background TextEdit PID never saved (2/2 runs). S down with
the Command flag failed, and so did Command down and up around S. A posted `x` did arrive
([evidence](2026-10-11-evidence.md), `2026-10-10-save-lock-delivery-*.json`). The files written
at about 30 s were autosave. Counting the 2026-10-08 hangs needs the engine's Cmd+S on an
Open-panel file.

## Runner

`node bench/textedit-save-lock.mjs` drives already-running background TextEdit through the
relay (`probeClient`, `relay: true`, `relayOptions: { changeReview: false, spaceProbe }`).
Each run opens a unique `/private/tmp/sleight-save-lock-*/trial.txt` with Cmd+O,
Cmd+Shift+G and the path, writes a distinct value through Accessibility, applies the run's
variant, then `pressKey("super+s")`, and waits up to 10 s for the bytes on disk. A hang is
recorded, never asserted. A hung document stays up 20 s more, then the run keeps the last
30 s of that PID's `log show`. `--dry-run` prints the plan as JSON and does not take the
live lock.

The Open panel shows the home folder: the runner never captures those stages, and published
JSON omits panel frames.

The gate comes first: 5 runs that post no settle event. If fewer than 3 of them hang, the run
records that Open panel doesn't reproduce the hang and stops. Otherwise 5 cycles run each
variant once: no event, a Shift `flagsChanged` pair (as `settleAfterTextWrite` posts), Escape,
a key-up alone, and an Apple Event read of the document's text sent to that PID without a
consent prompt.

Cleanup looks up TextEdit's PID at close time and closes only the owned document. TextEdit
keeps running. Saved documents close through Accessibility. Hung documents are left as they
are, so no Save panel is answered, and the live lock is kept.

`--delivery-check` types through the engine, with no Accessibility write, and requires
`pressKey("super+s")` to save within 2 s.

## Earlier evidence

The local research note of 2026-10-08 read AppKit disassembly and earlier TextEdit logs. It
didn't find a coordinated file write between the Accessibility edit and the hung save. It proposed
that an activity started by the edit awaited a main-thread callback. That remains an inference
because the earlier probes ended before AppKit's reported activity-dump delay.

The Shift mitigation posts two `flagsChanged` events to TextEdit's PID, with Shift set and
then cleared. It doesn't change text or use a HID event stream. Event delivery could finish
pending document work or reschedule an autosave monitor. Modifier state and the added delay
are also possible causes, which the earlier results do not distinguish.

An earlier runner on this file opened with `open -n -g` and posted Cmd+S to the PID. That
setup is the 0/3 arm. The posted chord left the file unchanged until autosave, so those
attempts don't measure the save lock.

## Cleanup result

The recorded owned launch is TextEdit PID `86808`, launched at `2026-10-10T05:40:54Z`.
The unchanged fixture is `/private/tmp/sleight-save-lock-khVl9r/trial.txt`. Window inspection
initially showed extra windows in that instance. Their contents were not read or changed. Cleanup refuses
to quit that process while other windows remain. The pre-existing TextEdit PID `52188` is separate
and remains untouched.

The later read-only check confirmed that the fixture was closed, and `/tmp/sleight-live.lock`
was released. It left the TextEdit process running and preserved unrelated windows and prompts.
Window Server inventory alone had not established closure, so release waited for the bounded
Accessibility check. The cleanup helper's read-only mode refuses unreadable document identities
and cannot send a close or quit action.

## Review correction

The read-only check above violated the live hold. It also left the owned TextEdit process running,
so its exit 0 did not establish complete cleanup. The receipt is retained as failed evidence.
Both native helpers now check the hold before live reads or actions. The cleanup runner checks it
before inspecting or acquiring the lock, including in read-only mode. A closed fixture no longer
counts as a quit process. Cleanup can reacquire an absent lock. After checking the recorded PID
and launch time, it quits only that launch if it has no windows. Restored windows still stop a quit.
The trial runner also attempted this cleanup after an unedited attach failure when it still launched
an isolated instance. The [follow-up handoff](2026-10-10-sim-savelock-2.md) records the remaining
owned-process cleanup.
